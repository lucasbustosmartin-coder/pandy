# Crear proyecto Supabase – Pandi

## Pasos

### 1. Crear proyecto en Supabase

1. Entrá a [supabase.com](https://supabase.com) e iniciá sesión.
2. **New project**: elegí nombre (ej. "pandi"), contraseña de base de datos y región.
3. Esperá a que el proyecto esté listo.

### 2. Obtener URL y API Key

1. En el dashboard: **Project Settings** (ícono engranaje) → **API**.
2. Copiá:
   - **Project URL** (ej. `https://xxxxx.supabase.co`).
   - **anon public** (para el frontend).
   - **service_role** (secret). Usala solo en scripts o entorno local, nunca en el frontend ni en el repo.

### 3. Archivo `.env` en la raíz del proyecto

En la carpeta Pandi creá `.env` (podés partir de **`.env.example`**: `cp .env.example .env`) con:

```env
SUPABASE_URL=https://TU_PROYECTO.supabase.co
SUPABASE_ANON_KEY=<TU_ANON_PUBLIC_KEY>
SUPABASE_SERVICE_ROLE_KEY=<TU_SERVICE_ROLE_KEY>
```

No subas este archivo a Git (está en `.gitignore`). Opcional **`.env.local`** para pisar claves solo en tu máquina (también ignorado).

### 4. Config para el frontend

- **Local:** con `.env` completo, ejecutá `npm run dev` — se genera **`config.js`** automáticamente antes de Vite (`node scripts/build-config.js`). Guía: **`docs/DESARROLLO_LOCAL.md`**.
- **Manual (legacy):** copiar `config.example.js` a `config.js` y pegar URL + anon.
- **Vercel:** `config.js` se genera en el build desde variables de entorno (ver `docs/GIT_Y_VERCEL.md`).

### 5. Scripts SQL

**Fechas de negocio (Argentina):** ejecutá primero `sql/helpers_fecha_argentina.sql` si armás la base a mano (antes de tablas con `DEFAULT` en `fecha`). En bases ya existentes, `sql/migracion_fecha_default_columnas_argentina.sql` alinea los DEFAULT de columnas `fecha`. Convención: `docs/FECHAS_ARGENTINA.md`.

**Compensación CC (USD-USD + intermediario, sin multicontraparte manual):** columna opcional `transacciones.compensacion_cc_monto_aplicado` (numeric, nullable). Script: `sql/migracion_transacciones_compensacion_cc_monto.sql`. Sin ejecutarlo en Supabase, el front puede recibir error al guardar el modal si intenta persistir ese campo. El sync inserta en CC la línea «Compensación parcial en cuenta corriente- …» o «Compensación total en cuenta corriente- …» vinculada a la transacción. Ver `docs/CUENTA_CORRIENTE_Y_CAJA.md`.

**Instrumentación ajustada manual (CC sin motor completo, sin MC):** columna `instrumentacion.instrumentacion_ajustada_manual` (boolean, default false). Script: `sql/migracion_instrumentacion_ajustada_manual.sql` (incluido en bootstrap tras `migracion_instrumentacion_multicontraparte.sql`). Si la columna no existe, los `select` embebidos `instrumentacion(...)` del listado de órdenes pueden fallar hasta ejecutar la migración. Con el flag en true, `sincronizarCcYCajaDesdeOrden` no recorre el motor completo `reglas_de_negocio` (análogo a multicontraparte manual) pero **no** activa la derivación multicontraparte ni el borrado de plantillas del checkbox MC; comisiones y CHEQUE+reglas siguen por las ramas `soloComisiones` / fallback ya cableadas en `main.js`. Tras cada `sync_cc_caja_orden` (o fallback) exitoso, la app **recalcula** el flag comparando las transacciones activas con la plantilla del tipo de orden (sin multicontraparte elegible; orden no anulada; al menos una transacción).

**RPC `sync_cc_caja_orden` — `usuario_id` en movimientos CC:** en producción/dev, volvé a ejecutar el script actual `sql/rpc_sync_cc_caja_orden.sql` (pegar en SQL Editor). Si el JSON no trae `usuario_id`, la función resuelve desde `transacciones` y `ordenes` antes que `p_usuario_id`. Nota: `sql/migracion_rpc_sync_cc_caja_orden_cc_usuario_desde_trx.sql` solo documenta el cambio; el cuerpo ejecutable está en `rpc_sync_cc_caja_orden.sql`.

**Clasificación ENUM (fase 0):** tipo `public.movimiento_clasificacion` y columnas `clasificacion_movimiento` (CC cliente, CC intermediario, caja) y `clasificacion_transaccion` (`transacciones`), default `LEGACY_SIN_CLASIFICAR`. Migración: `sql/migracion_movimiento_clasificacion_fase0_ddl.sql`. Luego reaplicar `sql/rpc_sync_cc_caja_orden.sql` (lee/escribe `clasificacion_movimiento` en el JSON; clave lógica del sync incluye el enum). Plan: `docs/PLAN_CLASIFICACION_MOVIMIENTOS_ENUM.md`.

**Clasificación ENUM (fase 1 — backfill):** `sql/migracion_movimiento_clasificacion_fase1_backfill.sql` — actualiza solo filas `LEGACY_SIN_CLASIFICAR` por capas (manual, compensación, cancelación, cierre multimoneda, préstamo regula B, comisión G/P, leyendas CC/caja, catch-all por orden/transacción; `transacciones` → `CC_FLUJO_OPERATIVO_TRX`). Requiere helpers `gp_concepto_es_*` de `migracion_gp_operativa_panel.sql`. Incluye `SELECT` de verificación al final. **Estado:** aplicado en **dev** y **producción** (2026-04-17). Detalle: `docs/PLAN_CLASIFICACION_MOVIMIENTOS_ENUM.md` § Fase 1.

**Clasificación ENUM (fase 2 — sync desde app):** `main.js` asigna `clasificacion_movimiento` en cada fila de CC/caja **antes** de invocar `sync_cc_caja_orden` (`enriquecerFilasSyncConClasificacionMovimiento`). Además, en **insert/update de `transacciones`** (modal guardar, compensatoria, cola import, plantillas de instrumentación, splits al cambiar monto/estado, Ganancia Pandy) se envía `clasificacion_transaccion` vía `asegurarClasificacionTransaccionEnPayload` (grueso `CC_FLUJO_OPERATIVO_TRX`, alineado al backfill fase 1). Tras desplegar el front, resyncs y altas no dejan filas nuevas en `LEGACY_SIN_CLASIFICAR` por omisión de la app. Ver plan § Estado fase 2.

**Clasificación ENUM (fases 3–4 — G/P, control de calidad, tests; fase 4 cerrada):** SQL de panel/detalle/control de calidad combina texto y `clasificacion_movimiento` (`sql/migracion_gp_operativa_panel.sql`, `migracion_gp_operativa_detalle.sql`, `migracion_control_calidad_vista_informe.sql`). Verificación opcional solo lectura: `npm run smoke:gp-operativa-readonly` (ver `docs/TESTING_E2E_GUIA.md`). Suite `npm run test:unit-clasificacion`. **Matrices producto** (ENUM↔bolsas G/P y transacciones→ENUM) **aprobadas** y enlazadas desde `docs/PLAN_CLASIFICACION_MOVIMIENTOS_ENUM.md` § **Próximos pasos** y § **Checkpoint de continuidad** (reanudar implementación o despliegue si se interrumpe el entorno). Siguiente bloque grande: **implementación fase 5** Modelo B — persistir `CC_RESULTADO_ECONOMICO_COMPENSATORIO` en filas concretas (motor/backfill/app) con criterios de producto **ya cerrados** en § **Definición fase 5 — Modelo B** del mismo plan.

**Anular orden — DELETE `comisiones_orden` / `orden_comisiones_generadas`:** el front (`ejecutarAnulacionOrdenCompleta`) elimina esas filas al anular. Las políticas RLS originales solo permitían DELETE con `abm_ordenes`. Ejecutar en **prod y dev** `sql/migracion_rls_comisiones_delete_anular_orden.sql` para permitir también `anular_orden` (misma condición en ambas tablas).

**Órdenes ya anuladas con comisiones huérfanas:** si quedaron filas en `comisiones_orden` / `orden_comisiones_generadas` para órdenes en `estado = 'anulada'` (anulación anterior al fix o DELETE fallido), limpieza puntual en SQL Editor: `sql/limpieza_comisiones_ordenes_anuladas.sql` (incluye `SELECT` de inspección y `DELETE` acotado; bloque comentado para una sola orden por `numero`).

**Órdenes anuladas con CC aún en `pendiente`:** el resync por orden no siempre corrige filas viejas ya persistidas. Parche solo **UPDATE** `pendiente` → `anulado` en `movimientos_cuenta_corriente` e `movimientos_cuenta_corriente_intermediario` (excluye manuales): `sql/limpieza_cc_pendiente_ordenes_anuladas.sql`. Para anular **todos** los movimientos no manuales que no estén ya `anulado` (incluye `cerrado`), más caja y transacciones de la instrumentación: `sql/fix_cc_anulado_estado.sql`.

**Paridad dev/prod:** el bootstrap generado (`npm run sql:bootstrap:dev`) debe dejar **23 tablas** en `public` alineadas a la app actual (incluye `app_config`, `orden_comisiones_generadas` y **`contraparte_vinculo`**). Si producción tiene más, revisá tablas legacy (`cc_modelo_reglas`) o auxiliares no incluidas en el bundle (p. ej. `contingencia_import_*`). Detalle: `docs/PANDY_DEV_SUPABASE.md`.

Los archivos en `sql/` se ejecutan en el **SQL Editor** de Supabase. **Órdenes — cliente obligatorio al insertar vía RPC:** la función `ordenes_insertar_con_proximo_numero` rechaza `p_cliente_id` nulo. En bases ya desplegadas, volvé a ejecutar el script actual `sql/ordenes_insertar_con_proximo_numero.sql` (DROP + CREATE) para alinear el servidor con la app. **USD-USD — modo de la tasa al cliente (descuento vs incremento):** `sql/migracion_ordenes_usd_usd_tasa_cliente_modo.sql` y luego el `ordenes_insertar_con_proximo_numero.sql` actual (columna `ordenes.usd_usd_tasa_cliente_modo`, parámetro RPC `p_usd_usd_tasa_cliente_modo`). **Órdenes — pata intermediario en efectivo o transferencia:** `sql/migracion_orden_intermediario_pago_transferencia.sql` (columna `intermediario_pago_transferencia` en `ordenes`) y reemplazar en la base la función `ordenes_insertar_con_proximo_numero` con el contenido actual de `sql/ordenes_insertar_con_proximo_numero.sql` (parámetros `p_intermediario_pago_transferencia`, `p_intermediario_transferencia_cobra_tasa`, `p_intermediario_transferencia_tasa`). **Tasa por transferencia al intermediario:** `sql/migracion_orden_intermediario_transferencia_tasa.sql` (`intermediario_transferencia_cobra_tasa` boolean, `intermediario_transferencia_tasa` numeric nullable como fracción 0–1, misma convención que `tasa_descuento_intermediario`). **CC intermediario en cruces con TC (ARS↔USD, EUR↔USD):** ejecutar `sql/migracion_reglas_comision_intermediario_cruces_tc.sql` (filas `es_comision` + `comision_intermediario`, incluye `estado_transaccion` pendiente y ejecutada). El front fusiona reglas al sincronizar si el código de catálogo no coincide con el canónico. Pares ARS↔EUR sin USD no están modelados en `patronTipoCambioOrden` del front hasta que se agregue ese cruce. Tras aplicar o actualizar la migración, **resincronizar CC/caja** de las órdenes afectadas. Bootstrap: `scripts/concat-bootstrap-dev-sql.js`.

**Panel G/P Operativa** (tarjeta en Inicio): `sql/migracion_gp_operativa_panel.sql` — columna `incluye_gp_operativo` en `tipos_movimiento_caja`, permiso `ver_inicio_gp_operativo`, helpers `gp_concepto_es_linea_comision_cc_gp` y `gp_concepto_es_comision_caja_ordenes_gp`, más **`gp_movimiento_cc_cuenta_es_linea_comision_gp`** y **`gp_movimiento_caja_ordenes_es_comision_gp`** (comisión del acuerdo detectada por **texto** o por **`clasificacion_movimiento`** ENUM, alineado al plan de clasificación — fase 3). Función `gp_operativa_resumen` (JSON con **siete** claves: `caja_manual`, `caja_ordenes` **solo cerrado** no anulado **excl.** comisión del acuerdo en caja, `cc_cliente` y `cc_intermediario` con **`estado IN ('pendiente','cerrado')`** no anulado **excl.** líneas de comisión del acuerdo (concepto o ENUM) **y excl.** movimientos con `clasificacion_movimiento = CC_RESULTADO_ECONOMICO_COMPENSATORIO` — **misma base que Saldos CC** para el flujo habitual; **`cc_resultado_economico_compensatorio`** suma solo esas filas CC (cliente + intermediario) para trazabilidad Modelo B **sin** duplicarlas en las filas de flujo; `comisiones_acuerdo_pandy` e `comisiones_acuerdo_intermediario` desde `comisiones_orden` por **fecha de la orden** más líneas CC de comisión **huérfanas**; la clave intermediario va **negada** en el agregado para que el total refleje el P&L de la empresa. El **total por moneda** = suma algebraica de las siete claves. Precondición: tipo y columnas `migracion_movimiento_clasificacion_fase0_ddl.sql` (en bootstrap dev va **antes** del panel). Re-ejecutar el script actualiza funciones si ya estaba desplegada.

**Orden recomendado al actualizar G/P + control de calidad (fase clasificación, 2026-04-17):** en SQL Editor, **1)** `migracion_gp_operativa_panel.sql` → **2)** `migracion_gp_operativa_detalle.sql` → **3)** `migracion_control_calidad_vista_informe.sql` (define `control_calidad_informe` y hace `DROP` de `gp_operativa_control_calidad` si existía). Opcional entre 2 y 3: `migracion_gp_operativa_control_calidad.sql` (RPC legacy); si luego corrés el paso 3, esa función se elimina de nuevo. **Histórico:** en la operación del 2026-04-17 se siguió ese orden en **dev y producción** para el paquete fase 3–4 entonces. **Estado documentado (sesión cierre 2026-04-17):** el `migracion_gp_operativa_detalle.sql` actual del repo incluye el arreglo **42P01** (`relation "v"`: cuerpo con `RETURN (SELECT …)` en lugar de `SELECT … INTO v` bajo `SET search_path = ''`). Ejecutar al menos el **paso 2** en **Supabase desarrollo** para alinear la función al repo. **Supabase producción:** en esta ronda **no** se aplicó ese reemplazo en servidor (política explícita: no tocar prod hasta decisión aparte); antes de pegar en prod, revisar diff y ventana de mantenimiento.

**Verificación post-despliegue con datos reales (solo lectura):** opcional `npm run smoke:gp-operativa-readonly` contra el proyecto que elijas (ej. producción), con variables dedicadas `SMOKE_GP_*` y confirmación explícita; no modifica tablas. Ver `docs/TESTING_E2E_GUIA.md` § Smoke G/P solo lectura.

**Detalle G/P Operativa** (modal «movimientos que suman» por fila): `sql/migracion_gp_operativa_detalle.sql` — función `gp_operativa_detalle(p_desde, p_hasta, p_bolsa)` devuelve un arreglo JSON con el **mismo criterio** que cada bolsa del resumen (`p_bolsa`: `caja_manual` | `caja_ordenes` | `cc_cliente` | `cc_intermediario` | `cc_resultado_economico_compensatorio` | `comisiones_acuerdo_pandy` | `comisiones_acuerdo_intermediario`), incluyendo exclusión de comisión por **ENUM** vía los helpers `gp_movimiento_*_gp` del panel. Si al crear la función aparece **42P01** `relation "v" does not exist`, es la versión vieja del script: actualizar desde este repo y re-ejecutar solo este archivo (comentario de cabecera del `.sql` y `docs/PLAN_CLASIFICACION_MOVIMIENTOS_ENUM.md` § Checkpoint). Cada objeto incluye **`modo_pago`** (columna «Medio de pago»): **`caja_manual`** → `Efectivo` / `Banco` / `Cheque` según `movimientos_caja.caja_tipo`; **`caja_ordenes`** y filas de **CC** con `transaccion_id` → nombre o código de `modos_pago` vía `transacciones.modo_pago_id`; líneas **sin** transacción → cadena vacía (en UI «–»). Las bolsas de comisión listan filas de `comisiones_orden` (id prefijado `co-` en JSON) más movimientos CC huérfanos; en **`comisiones_acuerdo_intermediario`** los **`monto`** del JSON van en **negativo** para coincidir con el signo del resumen. **Reparto Pandy + intermediario** (`comisiones_orden` con la misma orden y moneda para ambos beneficiarios): la fila **Pandy** ya refleja el neto empresa; **no** se listan de nuevo las filas intermediario desde `comisiones_orden` ni las líneas CC de intermediario equivalentes, para alinear el modal con el resumen G/P (sin doble resta). Parche único: `sql/migracion_gp_intermediario_reparto_sin_doble_resta.sql` (también integrado en `migracion_gp_operativa_detalle.sql`). Re-ejecutar el script actualiza la función **después** del panel (usa los mismos helpers). Incluida en bootstrap dev tras `migracion_gp_operativa_panel.sql`.

**Control de calidad** (menú lateral, vista dedicada): `sql/migracion_control_calidad_vista_informe.sql` — permiso **`ver_control_calidad`** (asignado a **admin** y copiado a todo rol que ya tuviera `ver_gp_operativo_control_calidad`), función **`control_calidad_informe(p_desde, p_hasta)`** devuelve JSON `ok`, `parejas_cc_caja` (`total`, `items` hasta 200), `trans_ejecutada_sin_registro_cc`, `trans_pendiente_sin_registro_cc`, `trans_ejecutada_cc_no_cerrado`, `trans_pendiente_cc_no_pendiente`, **`trans_anulada_sin_registro_cc`**, **`trans_anulada_cc_estado_no_anulado`** (cada uno `total` + `items`). Los chequeos por transacción usan la **fecha de la orden** en el período e **incluyen órdenes anuladas** (no se excluye `o.estado = 'anulada'`): en ejecutada/pendiente se exige coherencia con ambos libros de CC; en **transacción anulada** debe existir trazabilidad en CC y los movimientos **no manuales** deben quedar en estado anulado. Sin filtrar por `owner`. La función acepta también quien solo tenga **`ver_gp_operativo_control_calidad`** (compatibilidad). **Elimina** la función antigua `gp_operativa_control_calidad` del esquema `public`. Requiere `migracion_gp_operativa_panel.sql` aplicada antes. El front llama `control_calidad_informe` desde la vista Control de calidad. Script histórico de solo parejas: `sql/migracion_gp_operativa_control_calidad.sql` (útil en bases muy viejas antes del reemplazo). Clave JSON obsoleta aún tolerada en front: `trans_sin_mov_cc_cliente` (reemplazada por `trans_ejecutada_sin_registro_cc`). **Huecos históricos** (`transacciones.estado = anulada` sin fila CC en ningún libro): diagnóstico en `sql/auditoria_cc_transacciones_y_ordenes.sql` §3b; backfill opcional de marcadores en `anulado` con monto 0 (sin cambiar saldos): **`sql/reparacion_cc_trazabilidad_transacciones_anuladas_sin_movimiento.sql`** (vista previa + `INSERT` + verificación). La **app** al sincronizar CC por orden (`sincronizarCcYCajaDesdeOrden` en `main.js`) vuelve a insertar el mismo tipo de marcador si falta la fila, para que un resync no borre la huella.

**Vínculo intermediario ↔ cliente (misma persona):** tabla puente **`public.contraparte_vinculo`** — relación **1:1** (`UNIQUE` en `intermediario_id` y en `cliente_id`). Los movimientos CC **no** se mueven de tabla: siguen en `movimientos_cuenta_corriente` y `movimientos_cuenta_corriente_intermediario`. La app usa el vínculo en **Clientes** e **Intermediarios** (modales Editar: «Mismo registro que…»). En **Cuenta corriente**, el tipo **Cliente** muestra solo la CC cliente; el tipo **Intermediario** **lee** ambas tablas del par y unifica saldos/listados en pantalla (sin RPC adicional). En bases ya desplegadas: `sql/migracion_contraparte_vinculo_intermediario_cliente.sql` (idempotente). En bootstrap nuevo: `sql/supabase_complejidad_ordenes.sql` + RLS en `sql/supabase_rls_complejidad.sql` (lectura para `authenticated`; alta/edición/baja con `abm_intermediarios` **o** `abm_clientes`). Plan: `docs/PLAN_INTERMEDIARIO_CLIENTE_CC_UNIFICADA.md`.

**Órdenes — par vinculado en la misma fila (política actual; revoca la Fase 4 restrictiva):** el producto **permite** que `ordenes.cliente_id` y `ordenes.intermediario_id` coincidan con un par en `contraparte_vinculo` cuando la misma persona actúa como cliente e intermediario en **una** orden (coherente con la CC unificada al elegir tipo Intermediario). La validación en `main.js` que bloqueaba ese guardado fue **eliminada**. Si la base llegó a aplicar **`sql/migracion_ordenes_validar_no_par_vinculado_fase4.sql`** (trigger `tr_ordenes_no_par_vinculado`), ejecutar en **desarrollo** y **producción** **`sql/migracion_ordenes_quitar_trigger_par_vinculado.sql`** (idempotente: `DROP TRIGGER` + `DROP FUNCTION`). En el bootstrap dev, ese script va **después** de la migración Fase 4 (`scripts/concat-bootstrap-dev-sql.js`) para que un entorno nuevo no quede con el trigger activo.

**CC con intermediario — transacciones independientes (sin espejo `+mr` entre transacciones):** el canónico `sql/reglas_de_negocio_tabla.sql` ya **no** inserta la línea 2 `+mr` en CC cliente al cerrar E,E (cp_ic / ci_pc) **en el egreso** Int→Cliente para netear **entre** transacciones. En bases donde corría el antiguo `sql/migracion_reglas_cp_ic_ee_neteo_cliente_cruzadas.sql` (hoy obsoleto), ejecutar **`sql/migracion_reglas_cc_int_transacciones_independientes_quitar_espejo_mr.sql`** y **`sql/migracion_reglas_usd_ars_int_ee_ingreso_ejecutada_true_par_usd.sql`** si aplica, o **reaplicar** el bloque USD-ARS/ARS-USD+int desde `reglas_de_negocio_tabla.sql`. Luego **resincronizar** órdenes afectadas. Ver `docs/MODELO_CC_USD_ARS_TEORICO.md` § con intermediario.

**USD-USD+int o ci_pc, CHEQUE-ARS+int — transacciones pendientes sin movimiento CC (auditoría §1):** si el motor no encuentra regla porque **ninguna** pata del par está ejecutada aún (`contrapartida_ejecutada = false` en `main.js`) y en `reglas_de_negocio` solo existían filas `pendiente` con `contrapartida_ejecutada = true`, ejecutar **`sql/migracion_reglas_pendiente_contrapartida_false_usd_usd_int_y_cheque_tx4.sql`** (idempotente) o reaplicar el bloque actual de `sql/reglas_de_negocio_tabla.sql`. Luego **Refrescar** CC / reabrir la orden para `sync_cc_caja_orden`.

**CHEQUE-ARS+int — autocompletar deja las 4 transacciones en pendiente:** si al sincronizar faltan patas CC (p. ej. no aparece movimiento con **Trans. 4**) o el toast «sin regla», faltan filas `pendiente` en `reglas_de_negocio` para Tx1/Tx2 (cliente), Tx3 (P→Int) y **Tx4** (Int→Pandy, `monto_efectivo_intermediario`) con `contrapartida_ejecutada` acorde al motor. Ejecutar **`sql/migracion_reglas_cheque_ars_int_tx1_tx2_tx3_pendiente.sql`** (idempotente; incluye Tx4) o **`sql/migracion_reglas_cheque_ars_int_tx4_pendiente.sql`** si ya tenías el parche antiguo sin Tx4, o reaplicar `sql/reglas_de_negocio_tabla.sql`. Ver `docs/CHEQUE_ARS_INTERMEDIARIO.md`.

**USD-ARS / ARS-USD sin intermediario, ambas patas pendientes (P,P):** mismo criterio de `contrapartida_ejecutada = false` en el front; si en Supabase faltan filas `pendiente` + `false` para ingreso C→Pandy y egreso Pandy→C, ejecutar **`sql/migracion_reglas_usd_ars_ar_usd_pp_contrapartida_false.sql`** en dev y prod, o reaplicar **`sql/migracion_reglas_todos_cruces_dos_monedas_sin_int_canonico.sql`** (reemplaza el bloque de cruces sin int.; ahora **12** filas por tipo). Evita el toast «no coinciden con ninguna regla de negocio» al instrumentar solo con pendientes.

**USD-ARS / ARS-USD + intermediario, patrón `ci_pc`, P,P (ambas pendientes):** el motor usa `contrapartida_ejecutada = false` en ingreso Cliente→Intermediario y egreso Pandy→Cliente; si solo existían filas `pendiente`+`true` en el ingreso y no había egreso **pendiente**+`false`, la sync no persiste CC y aparecen avisos «sin fila en reglas». Ejecutar **`sql/migracion_reglas_usd_ars_ars_usd_int_ci_pc_pp_contrapartida_false.sql`** (idempotente) o reaplicar el bloque ci_pc de `sql/reglas_de_negocio_tabla.sql`. Ver `docs/REG_NEG_USD_ARS_INT_PASO1.md`. Luego **Refrescar** CC / resincronizar la orden.

**USD-ARS / ARS-USD + intermediario, `ci_pc`, E,P (cobro ejecutado, entrega pendiente):** el egreso Pandy→Cliente **pendiente** matchea con **`contrapartida_ejecutada = true`** (ingreso C→I ya ejecutado). Sin esa fila, el motor avisa «sin fila en reglas». Ejecutar **`sql/migracion_reglas_usd_ars_ars_usd_int_ci_pc_ep_egreso_pendiente_contrapartida_true.sql`** o reaplicar `sql/reglas_de_negocio_tabla.sql`.

**USD-ARS / ARS-USD + intermediario, `ci_pc`, P,E (ingreso C→I pendiente, egreso P→C ejecutado):** el ingreso va con **`pendiente` + `contrapartida_ejecutada = true`**; hace falta fila **`entidad_cc = intermediario`** (+mr en moneda recibida del acuerdo) para que la CC del intermediario refleje el cobro pendiente. Ejecutar **`sql/migracion_reglas_usd_ars_ars_usd_int_ci_pc_pe_intermediario_ingreso_pendiente_true.sql`** o reaplicar `sql/reglas_de_negocio_tabla.sql`.

**cp_ic E,E — par ± en ingreso Cliente→Pandy (moneda recibida):** si con ARS-USD+int o USD-ARS+int (patrón cp_ic) y **ambas** transacciones ejecutadas la CC cliente muestra saldo fantasma en la moneda **recibida** del acuerdo (ARS o USD), ejecutar **`sql/migracion_reglas_cp_ic_ingreso_ee_par_moneda_recibida.sql`** (idempotente) o reaplicar `reglas_de_negocio_tabla.sql`. Documentación: `docs/REG_NEG_ARS_USD_INT_PASO1.md`, `docs/REG_NEG_USD_ARS_INT_PASO1.md`. Resincronizar órdenes afectadas.

**Patrón `ci_pc` con varias entregas en moneda entregada** (ej. efectivo Pandy→Cliente + transferencia Intermediario→Cliente en la misma orden): si la CC del cliente queda con un «pendiente de cobro» igual al total `monto_entregado` pese a tener todas las transacciones ejecutadas, ejecutar `sql/migracion_reglas_ci_pc_egreso_pandy_monto_transaccion.sql` (idempotente: pasa `monto_origen` de `me` a `monto_transaccion` en egresos Pandy→Cliente `compromiso_pago`). Si con **todas** las transacciones ejecutadas (E,E) falta la **segunda** pata del egreso (`linea = 1`, `contrapartida_ejecutada = true`), ejecutar **`sql/migracion_reglas_ci_pc_egreso_pandy_ee_linea1_negativo.sql`** (en el repo actual inserta/actualiza **linea 1** en moneda **recibida** con **+mr_prorrateado**, alineado a `reglas_de_negocio_tabla.sql`; **no** vuelve a escribir el patrón viejo ± en moneda entregada). Luego **resincronizar** las órdenes afectadas.

**USD-ARS / ARS-USD / EUR+int, `ci_pc`, E,E — error «CC no netea a cero» (residual −me en moneda entregada):** suele ser **linea 1** del egreso P→C todavía en moneda **entregada** o con `monto_transaccion` en lugar de **`mr_prorrateado`** en moneda **recibida**. Corregir con **`sql/migracion_reglas_ci_pc_ee_egreso_linea1_mr_prorrateado_moneda_recibida.sql`** (fase A + fase B relajada) o reaplicar `sql/reglas_de_negocio_tabla.sql`. **Si en local sigue el error tras “correr el SQL” en dev/prod:** comprobar que el `.env` de Vite apunta al **mismo** proyecto Supabase (URL/anon key) y ejecutar **`sql/verificar_reglas_ci_pc_ee_egreso_linea1.sql`** en esa instancia. Ver `docs/REG_NEG_USD_ARS_INT_PASO1.md` § E,E `ci_pc`.

**USD-USD + intermediario, `cp_ic`, ingreso pendiente y egreso Int→Cliente ejecutado (P,E):** si la CC del intermediario neteaba en cero o no mostraba deuda Pandy (me + comisión int.), ejecutar `sql/migracion_usd_usd_int_cp_ic_intermediario_pe_deuda.sql` (idempotente). Quien use el script único `sql/ejecutar_supabase_cc_int_cp_ic_comision_y_regenerar_eur.sql` desde cero ya recibe las filas al día.

**Cruces dos monedas + intermediario (`USD-ARS`, `ARS-USD`, y EUR+int espejados), `cp_ic`, P,E:** si en CC intermediario el egreso Int→Cliente ejecutado (contrapartida pendiente) aparecía como **par +/−** que neteaba en cero en lugar de **una sola línea −me** (alineado a USD-USD+int), ejecutar `sql/migracion_reglas_cp_ic_int_pe_intermediario_una_sola_linea_negativa.sql` (idempotente; afecta cualquier fila que cumpla el criterio, incl. EUR clonados). Alternativa: volver a correr `sql/ejecutar_supabase_cc_int_cp_ic_comision_y_regenerar_eur.sql` tras actualizar el repo. Luego **resincronizar** órdenes afectadas.

**USD-USD + intermediario, patrón `ci_pc` (Cliente→Intermediario + Pandy→Cliente):** si faltaba el cobro **mr** en CC intermediario o la **Comisión del acuerdo** (mr−me) en CC cliente con tasas %, ejecutar `sql/migracion_usd_usd_int_ci_pc_cc_intermediario_ingreso_y_comision.sql` (idempotente). También está en `sql/ejecutar_supabase_cc_int_cp_ic_comision_y_regenerar_eur.sql` (§2c). **Motor actual:** el egreso Pandy→Cliente **no** genera fila en CC intermediario (sigue en reglas para compatibilidad; `main.js` lo omite en `ci_pc`); el saldo Pandy–intermediario queda en **+mr** del ingreso C→I y la comisión int. Ver `docs/USD_USD_CON_INTERMEDIARIO.md`. Tras migrar, **Refrescar** CC o re-guardar estado de transacción en la orden.

**USD-USD, cobro ejecutado y entrega al cliente pendiente (E,P):** matriz canónica: cobro CC **−me**, comisión **−(mr−me)** **cerrada**, egreso pendiente solo **+mr**. Bases legadas (cobro −mr, comisión pendiente +318, o segunda línea −me en el egreso): ejecutar **`sql/migracion_reglas_usd_usd_ep_cobro_me_comision_cerrada.sql`** (idempotente). `sql/migracion_usd_usd_sin_int_comision_ep_gp.sql` mantiene solo el `INSERT` de la fila `es_comision` E,P; el bootstrap `sql/reglas_de_negocio_tabla.sql` ya trae todo al día.

**USD-USD (sin o con intermediario), ambas patas pendientes (P,P) y comisión implícita:** si en CC cliente aparece **+mr** en «Compromiso a Cobrar» (ingreso) y otra vez **+mr** en «Compromiso de Pago» (egreso pendiente) junto con **−me** y la comisión **mr−me**, el saldo duplica el nominal. Ejecutar **`sql/migracion_reglas_usd_usd_pp_me_compromiso_sin_mr_egreso_false.sql`** (idempotente) o reaplicar el bloque USD-USD de `sql/reglas_de_negocio_tabla.sql`. Ver `docs/USD_USD_SIN_INTERMEDIARIO.md` § P,P. Luego **Refrescar** CC.

**Lecturas masivas (tamaño de página PostgREST):** clave **`supabase_select_page_size`** en `app_config` (número entre **100** y **10000**, por defecto **1000**). La app la usa en `pandiSupabaseFetchAll` (cuenta corriente, transacciones por instrumentación, etc.) y en el límite de listas de clientes/intermediarios en modales. Debe ser **≤** al `max-rows` configurado en tu instancia Supabase/PostgREST (ej. 5000). Script: `sql/migracion_app_config_supabase_select_page_size.sql`. Editable en **Seguridad** (solo Admin); tras cambiar, conviene **recargar** la app.

**USD–USD con intermediario, comisión fija en USD (dos importes + intermediario por ID):** la app lee `app_config.key = usd_usd_comision_fija_config` (JSON: `intermediario_id`, `opcion_a`, `opcion_b`). Ejecutar `sql/migracion_app_config_usd_usd_comision_fija_intermediario.sql` en Supabase si la clave no existe. Configuración en **Seguridad** (solo admin). Si `intermediario_id` está vacío, se mantiene compatibilidad por nombre con la palabra «nacho».

**Movimientos de caja (alta / edición / anulación por separado):** en bases que aún usan `abm_movimientos_caja`, ejecutar `sql/migracion_permisos_movimientos_caja_granular.sql` (reemplazo en catálogo, migración de roles y RLS). Bootstrap dev lo incluye en el concat. Hasta migrar, la app trata `abm_movimientos_caja` como equivalente a los tres permisos granulares **solo en la UI**; las políticas RLS nuevas usan `has_permission('alta_movimiento_caja')`, etc., por lo que si el botón aparece pero el INSERT falla, falta ejecutar esa migración en Supabase.

**Seguridad → permisos por rol** (toggles que insertan/borran en `app_role_permission`) requieren `sql/migracion_permisos_rol_editable.sql`; sin esas políticas RLS y `GRANT INSERT, DELETE`, los cambios no persisten aunque el interruptor en pantalla parezca cambiar. **Perfiles nuevos desde la UI** (insert/delete en `app_role`, distintos de admin/encargado/visor): `sql/migracion_app_role_gestion_assign_roles.sql` — actualiza `set_user_role` y RLS de `app_role`; en instalaciones nuevas queda reflejado en `sql/supabase_seguridad.sql`.

**Nombre visible por usuario** (columna `user_profiles.display_name`; listados y exportaciones muestran nombre o, si falta, email): en bases ya desplegadas ejecutar `sql/migracion_user_profiles_display_name.sql` (idempotente: `ADD COLUMN IF NOT EXISTS`, `DROP FUNCTION IF EXISTS get_users_for_admin()` y recrear con cuatro columnas incl. `display_name`, RPC `admin_set_user_display_name` solo con permiso `assign_roles`, RPC `set_my_display_name` para el usuario autenticado). En instalaciones nuevas el DDL y las funciones van en `sql/supabase_seguridad.sql`. El bootstrap dev concatena la migración tras `supabase_seguridad.sql` (`scripts/concat-bootstrap-dev-sql.js`).

**Etiquetas en listados para todos los roles** (órdenes, CC, cajas): la SELECT directa a `user_profiles` con varios UUID solo devuelve filas permitidas por RLS (fila propia y, si aplica, vista admin). Para que usuarios sin `assign_roles` vean `display_name`/email de quien cargó una orden u otro registro, ejecutar `sql/migracion_user_profiles_labels_for_ids_rpc.sql` (función `user_profiles_labels_for_ids(uuid[])` **SECURITY DEFINER**, solo expone `id`, `display_name`, `email`). El front usa esta RPC en `fetchMapaEtiquetaUsuarioPorIds` con respaldo a la SELECT anterior.

**Panel Inicio — tarjetas pendientes por separado:** `sql/migracion_permisos_inicio_tarjetas_pendientes_split.sql` define `ver_inicio_ordenes_pendientes` y `ver_inicio_transacciones_pendientes` y los asigna a cada rol que ya tenía `ver_inicio_pendientes`. Cuando definas tablas para la app, creá los DDL en `sql/` (ej. `supabase_*.sql`) y ejecutalos en ese orden. Menús **Tipos de operación** y **Reglas de negocio (CC)** requieren permisos `abm_tipos_operacion` y `abm_reglas_negocio` (incluidos en `migracion_permisos_ordenes_transacciones.sql` y `migracion_permiso_abm_reglas_negocio.sql`; parche suelto `migracion_permiso_abm_tipos_operacion.sql` si la base ya tenía permisos viejos). Bootstrap: `docs/PANDY_DEV_SUPABASE.md`. **Tipos de operación (export):** `docs/tipos_operacion_rows.csv`; regenerar SQL de carga con `npm run sql:seed:tipos-operacion` → `sql/seed_tipos_operacion_from_docs_csv.sql` (ver comentarios en ese archivo). **Reglas de negocio (export con id):** `docs/reglas_de_negocio_rows.csv` o `docs/reglas_de_negocio_rows (2).csv`; `npm run sql:seed:reglas-de-negocio` → `sql/seed_reglas_de_negocio_from_docs_csv.sql`; detalle y riesgos en `docs/reglas_de_negocio_rows_README.md`. Para **marca / nombre visible en pantalla** (white-label): `sql/migracion_app_empresa.sql` y `docs/APP_EMPRESA.md`. Para **movimientos de CC sin orden** (manual + permiso + pagador/cobrador + tipos caja fijos + `orden_id` nullable): `sql/migracion_cc_movimiento_manual.sql`, `sql/migracion_cc_manual_pagador_cobrador.sql`, `sql/migracion_tipos_caja_cc_manual.sql`, si aplica `sql/migracion_cc_movimientos_orden_id_nullable.sql`, **edición/anulación/auditoría/caja vinculada:** `sql/migracion_cc_manual_editar_eliminar_auditoria.sql`, y `docs/CC_MOVIMIENTO_MANUAL.md`. Para **anular orden** con impacto en CC/caja usando el permiso `anular_orden`: `sql/migracion_rls_anular_orden_cc_caja.sql` (después de permisos órdenes/transacciones y RLS CC manual). Para **instrumentación manual multicontraparte** (ARS-USD / USD-ARS sin intermediario): `sql/migracion_instrumentacion_multicontraparte.sql`, `sql/migracion_transaccion_chk_pagador_cobrador_multicontraparte.sql` (CHECK pagador/cobrador con dos clientes distintos) y `docs/INSTRUMENTACION_MANUAL_MULTICONTRAPARTE.md`. **Signo «Compromiso a Cobrar» (ingreso pendiente hacia Pandy/intermediario en CC cliente):** parche idempotente `sql/migracion_reglas_compromiso_cobrar_ingreso_pendiente_signo_positivo.sql` en bases que ya tenían `signo = -1`; el canónico del repo está actualizado en `sql/reglas_de_negocio_tabla.sql`.

### 7. Security Advisor (avisos habituales)

El dashboard **Advisors → Security Advisor** (splinter) puede mostrar lo siguiente; no todo exige cambio de producto:

| Aviso | ¿Corregir en BD / app? | Qué hacer |
|--------|-------------------------|-----------|
| **Function Search Path Mutable** (`public.transaccion_pertenece_a_orden`) | **Sí.** Es buena práctica fijar `search_path` en funciones `SECURITY DEFINER` o expuestas; aquí aplica el mismo criterio. Ejecutá **`sql/migracion_transaccion_pertenece_a_orden_search_path.sql`** en el SQL Editor (prod y dev). En instalaciones nuevas que usen `sql/migracion_cc_caja_orden_robusto.sql` completo, la función ya queda con `SET search_path = public, pg_temp`. |
| **Public Storage Buckets / listado** (`tipo-operacion-iconos`) | **Corregido en el script del repo.** El Advisor **0025** avisa si hay una política **SELECT** muy amplia en `storage.objects` (permite listar todo el bucket). Para bucket **público** no hace falta: el acceso por URL pública (`/object/public/...`) no depende de esa política; la app solo usa **upload** + **getPublicUrl** (sin `list()`). El script `sql/storage_bucket_tipo_operacion_iconos.sql` **no** crea política SELECT; si tu base tenía `tipo_op_iconos_select_public` heredada, ejecutá el `DROP POLICY` del mismo archivo o el bloque DROP del parche aplicado vía MCP. |
| **Leaked Password Protection** (Auth) | **Recomendado activarlo** (no es SQL del repo). En el dashboard: **Authentication** → **Attack Protection** (o **Providers** / **Password** según versión del panel) → activar **Leaked password protection** (HaveIBeenPwned). Mejora el registro/login sin tocar la app. |
